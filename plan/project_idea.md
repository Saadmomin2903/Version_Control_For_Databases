Git-Style Versioned Lakehouse with Apache Iceberg & Project Nessie
This architecture uses Apache Iceberg tables on cloud storage (S3/MinIO) with Project Nessie as a Git-like catalog, enabling full data-version control across a medallion (bronze/silver/gold) pipeline. Raw data is ingested into a Bronze branch, cleaned/transformed in a Silver branch, and aggregated in Gold (production). Each layer’s changes are done on dedicated Nessie branches so data engineers can “write–audit–publish” (WAP) changes safely: new data is written to an isolated branch, audited, then merged if quality checks pass[1][2]. This ensures data quality and rollback ability at every stage. Nessie’s Git-like semantics let us treat the data catalog “as code” – engineers can branch, tag, and commit tables just as they do with software code[3][4].
Architecture Overview
Storage & Table Format: We use Iceberg tables on object storage (e.g. Amazon S3 or on-prem MinIO). Iceberg is a modern open table format that presents data files as versioned tables[5]. It provides ACID transactions, full schema evolution, hidden partitioning and time-travel queries, giving data-warehouse features on a data lake[6]. Multiple compute engines (Spark, Trino, Dremio, etc.) can read and write Iceberg tables safely in parallel.
Metadata Catalog (Project Nessie): Nessie serves as the centralized catalog for Iceberg. It runs as a lightweight REST service (deployable in Docker or K8s) and stores table metadata in a Git-like store (using RocksDB, Cassandra/DynamoDB backend, etc.)[7][4]. Nessie lets us create branches and commits on the entire catalog: each Iceberg table has pointer chains (manifests) to its data files, and Nessie tracks the current pointer per branch. You can branch, tag, and merge catalogs just like a Git repo[4][6]. In practice, we configure Iceberg’s REST catalog to point at our Nessie server (e.g. nessie://host:port/api/v1?catalog=hadoop), so that reads/writes go through Nessie. This replaces traditional Hive Metastores, streamlining deployment (no external metastore) and unlocking features like cross-table transactions and catalog versioning[8][9].
Compute Engines: Data transformations are done in Python (or Spark). We use Polars (a fast Rust-based DataFrame library) for ETL on small-to-medium datasets – Polars often runs much faster than Pandas/Spark in this regime[10]. The transformed Polars DataFrames are converted to Apache Arrow tables, which PyIceberg then writes into Iceberg tables on Nessie branches[11]. PySpark is an alternative engine; you can use Spark with Nessie by adding the nessie-spark-extensions library and pointing Spark SQL’s catalog at Nessie (as shown in tutorials[12]).
Orchestration: We orchestrate the multi-stage pipeline with a scheduler (e.g. Airflow or Mage). Each task specifies the Nessie branch and Iceberg catalog URI to use. For example, the Bronze loader task writes to branch bronze, then the Silver task checks out branch silver, and so on. After each write, the task runs data-quality checks. If checks pass, a merge is triggered (e.g. merge bronze_orders table branch into bronze and then bronze into silver). If checks fail, we abort the merge and alert. This implements the Write–Audit–Publish (WAP) pattern end-to-end[1][13]. Mage (or Airflow) can be configured to send alerts (Slack/webhooks) on failures to notify data engineers immediately.
Query & Consumption: Any SQL/BI tool can query the Iceberg tables via Nessie. For example, Trino or Dremio (Arctic) can connect to the Nessie-backed catalog and run analytics queries against each branch or merged table. BI tools like Superset or Redash can be pointed at Trino to visualize the Gold-layer data. For machine learning, data scientists can snapshot a branch’s state (e.g. the latest merged gold tables) and export it to train models. Because each Nessie branch is a full snapshot of the schema and partitions, one could even branch the Gold layer, run experimental transformations, and then merge back if results are good.
Medallion Pipeline & Branching Flow
We adopt a three-tier medallion architecture[14]. Raw ingested data (e.g. CSV/JSON from sources) goes into the Bronze layer with minimal cleansing. The Silver layer holds cleaned, conformed data (e.g. deduplicated, type-corrected) suitable for general analysis. The Gold layer contains curated aggregates or feature sets for reporting/ML. This layered approach “systematically improves data quality” at each stage and simplifies governance[14][15].
The key innovation here is applying git-like branching to each layer and table[16]. For each pipeline stage:
- Layer Branches: We create a Nessie branch for each layer (named like bronze, silver, and main/gold).
- Table Branches: Within each layer branch, each table write happens on its own short-lived branch (e.g. bronze_orders_table_v3). This isolates in-progress changes.
The flow follows Write–Audit–Publish[1]:
- Write: A task writes new or updated data into an Iceberg table on a branch derived from the layer branch. The IcebergTableManager (or Spark) will create the table if missing.
- Audit: We run quality checks on the data in that branch (e.g. row counts, null-checks). Engineers can also query the branch to inspect data. Because the branch is isolated, queries won’t see it in the main line.
- Publish: If checks pass, the table branch is merged into its layer branch, then the layer is merged upward (e.g. bronze_orders_table_v3 → bronze → silver). If a check fails, we abort the merge, send an alert, and optionally delete the branch. This ensures only validated data propagates[2][13].
This strategy yields several benefits: data isolation and safe testing (new data can be inspected in a branch without affecting others), high data integrity (no bad data enters main tables), and clear lineage/auditing (Nessie keeps a history of all commits and merges)[17]. It embodies CI/CD practices for data: merges only occur on success and failures are logged. Branches can be rolled back or cherry-picked if needed, just like source code.
Technical Stack and Concepts
Apache Iceberg (Table Format): Iceberg tables on S3/MinIO store data in Parquet/Avro files with an evolving metadata layer. Key features: ACID transactions, time-travel queries (query past snapshots), schema/partition evolution, and hidden partitioning[6]. These enable data-warehouse features on open data. For example, Iceberg ensures readers get a consistent snapshot even with concurrent writers. We use PyIceberg (Python API) or Spark SQL to write/read tables.
Project Nessie (Catalog & Version Control): Nessie is essentially “Git for data”[4][6]. It stores the active metadata pointer for each table and a full commit history. You can branch/tag/merge the entire catalog. This lets us treat table updates as commits. Key concepts: references (branches/tags), commits, and transactions. Nessie allows storing the table metadata pointer in an eventually-consistent way (important for object stores) without a Hive Metastore[8]. We use Nessie’s REST API (via PyIceberg or Spark connectors) to manage branches programmatically.
Data Processing (Polars / Spark): For transformations we prefer Polars in Python due to speed on moderate data volumes[10]. Polars DataFrames can be converted to Apache Arrow tables and written to Iceberg via PyIceberg[11]. For very large scale, Spark+Iceberg is an option (using Nessie’s Spark extensions). In either case, jobs read from Nessie branches and write new snapshots.
Orchestration (Airflow / Mage): We use a workflow engine to sequence Bronze→Silver→Gold steps. Each task sets the Nessie branch (via Iceberg catalog config) it writes to. For example, an Airflow task might configure spark.sql.catalog.my_catalog.warehouse=s3://..., spark.sql.catalog.my_catalog.uri=http://nessie:19120/api/v1, spark.sql.catalog.my_catalog.ref=bronze. After loading and quality-checking, a PythonOperator or Mage script can call the Nessie client to merge branches. Notification hooks (e.g. Slack) alert on failures[13].
Query & BI Tools: Any engine with Iceberg/Nessie support can query the data. Trino/Presto, Dremio/Arctic, or even Spark SQL can be pointed at the Nessie catalog to run analytics on any branch. For example, after the Gold layer is updated, we can connect Superset or Redash to Trino and build dashboards on the latest data. Because Nessie retains history, one can even query old snapshots by checking out past commits. For ML use cases, the latest Gold tables (or any branch) can be exported to Pandas/NumPy, or accessed via Spark for training.
Implementation Plan
Set Up Nessie Catalog: Deploy a Nessie server (e.g. via Docker or Kubernetes) and select a backend store. By default, Nessie can run with an embedded RocksDB or Cassandra/DynamoDB for production. Configure Iceberg (PyIceberg or Spark) to use the Nessie REST catalog: e.g. catalogType=nessie, pointing to the Nessie endpoint. Create a top-level namespace/database (e.g. ecommerce) in Nessie to hold tables. Initialize branches: typically main (gold), bronze, and silver.
Ingest Raw Data (Bronze Branch): Write a loader job (Polars/PySpark) that reads raw input (CSV/JSON/Parquet). For each table, create or replace the Iceberg table on Nessie branch bronze. For example:
Check out Nessie branch bronze.
Use PyIceberg to create namespace ecommerce and table (e.g. orders_bronze) if not exists.
Append the raw data to the Bronze Iceberg table.
After writing, register this as a commit on the bronze branch.
Transform to Silver and Gold: Create subsequent jobs (Airflow tasks):
Silver Stage: Task checks out silver branch (starting from where it left off, usually empty initially), reads from the latest bronze data, applies cleaning/transforms, and writes to a Silver table (on a new branch e.g. silver_orders_v1). Run data-quality checks on that branch. If they pass, use Nessie API to merge silver_orders_v1 into silver. Then merge silver into main (which we treat as Gold) if ready.
Gold Stage: On a gold or main branch, perform any final aggregations or schema finalizations. This might simply be merging silver into main once testing is done.
At each stage, use short-lived branches for changes. For example, creating a new branch off silver for each table update isolates failures[16][2]. If a quality check fails, abort the merge and notify. This Write–Audit–Publish flow prevents bad data from reaching the Gold tables[13][17].
Quality Checks and CI: Integrate automated tests in each job. For instance, after writing Silver data, verify record counts or business rules. If a check fails, raise an exception so the pipeline halts and no merge occurs. Configure the orchestrator to send alerts on failure. Optionally, maintain a manual review step: an analyst can query the isolated branch via Trino (by switching the Nessie ref) to investigate issues before merging.
Querying and Visualization: Once the Gold tables are merged, connect an analytics layer. For example, set up Trino with the Nessie catalog URI to query the Iceberg tables in main. Data analysts can use SQL to explore the data (branch-merged state). For BI, link Superset/Redash to Trino. For ML, use Spark or Python to read Iceberg snapshots via Nessie and export to NumPy/Pandas as needed. Nessie’s versioning means you can recreate any historical state (e.g. to troubleshoot a data anomaly or retrain on past data) by simply checking out the corresponding branch or tag.
Use Cases & Benefits
Safe Data-as-Code Experimentation: Teams can branch the data pipeline just like code. For example, trial a new algorithm on the Silver data by writing to a feature branch. Because branches are isolated, production (gold) remains untouched[9][6]. Once validated, the branch is merged in. This promotes reproducibility and safer experimentation.
Data Lineage and Auditing: Every table change is a Nessie commit with metadata. You can audit who changed what and when. Need to roll back a bad load? Simply revert the branch commit. The history also shows exactly which version of data powered each analysis – critical for compliance.
Improved Governance: By using a Git-like model, we gain version tags and immutable history for all data tables[4][9]. This lays groundwork for policies (e.g. who can merge to Gold) and meets regulatory requirements for data traceability.
Concurrent Development: Different teams can work in parallel on the data lake. One team can refresh the Bronze customer table while another develops new features on historical data. Their branches don’t conflict until intentional merges.
Performance & Flexibility: Using Polars allows faster dev turnaround on moderate data, and Iceberg’s partitioning keeps queries fast. Nessie adds no runtime overhead for readers – it’s just a metadata layer. All tools are open-source, avoiding vendor lock-in.
Unique Selling Points (USP)
Git-like Semantics for Data: This project uniquely applies version control to the entire data lake. Unlike traditional pipelines, we can branch the lakehouse schema/data and treat it like code[4][6]. This is still rare in tutorials and offers modern “data-as-code” workflows (borrowed from DevOps) to data engineering.
Integrated Versioning & QA: By embedding version control into the pipeline (Write–Audit–Publish), we enforce data quality as part of CI/CD. Bad data literally never merges into production. This end-to-end approach (from raw ingest to BI) under Nessie’s control is more transparent than black-box managed lakehouses.
Tooling Flexibility: Swapping Spark for Polars shows we’re not tied to a heavyweight engine. We demonstrate that Python/Rust-based tools can power a full lakehouse, which may appeal to data teams preferring Python ecosystems.
Metadata Visibility: Every commit in Nessie is inspectable. You can browse branches and commits in Nessie’s UI or via API to see exactly how tables evolved. This deep insight into lineage goes beyond simpler systems.
Prerequisites & Setup
Knowledge/Skills: Familiarity with data engineering concepts (ETL, DAGs) and tools (Python, SQL). Experience with Apache Iceberg or Hive metastore concepts is helpful.
Infrastructure: A distributed file store (S3, or on-prem MinIO/HDFS) and compute for transformations (a Spark cluster or Python environment).
Services: Install Nessie (we can use Docker: docker run -p 19120:19120 projectnessie/nessie:latest). In Iceberg configs, set catalogType=nesie and point nessie.uri to it. Ensure you have PyIceberg or the Iceberg Spark connector with Nessie support (e.g. add Maven artifact nessie-spark-extensions).
Orchestration: Deploy Airflow/Mage or similar. Configure pipeline tasks with the Nessie catalog URI and branch names.
Storage Setup: Create the bucket/namespace (e.g. minio://bucket/data) and ensure Iceberg can write there.
Initial Tables: You may preload an initial (empty) table schema on the Bronze/main branch so that downstream jobs know the schema. Alternatively, let the first Bronze job create tables.
BI/Query Tools: Install/connect Trino or Dremio (Arctic) for querying Iceberg. Ensure it’s configured to use the same Nessie catalog. For example, in Trino’s catalog properties set iceberg.catalog.type=NESSIE.
All configuration can be done ahead of time; the pipeline logic then simply reads from and writes to the Nessie-based catalog.
Implementation Checklist
Deploy Nessie (Docker/K8s) and verify it’s accessible (e.g. via Nessie CLI or UI). Create the repository and initial branches (main, bronze, silver).
Configure Iceberg (PyIceberg or Spark) to use Nessie’s REST catalog. Test creating a dummy table and committing to ensure connectivity.
Write the Bronze Loader: A job that reads source data and writes to an Iceberg table on branch bronze. Commit this data to Nessie.
Write the Silver Transformer: A job that checks out from bronze, cleans/transforms data with Polars (or Spark), and writes to an Iceberg table on a new branch (off silver). Run QA checks, then merge that branch into silver, and silver into main.
Monitor and Alert: Set up failure alerts (e.g. Slack) for when a QA check fails, preventing a merge.
Connect Query Layer: Point your SQL engine (Trino/Presto/Dremio) at the Nessie catalog. Run sample queries on the main (Gold) tables to verify data.
Iterate: Add Gold-level aggregations or additional features in new branches as needed. Use Nessie tagging to mark releases or snapshots (e.g. tag-v1.0).
By following this plan, you’ll build an advanced, fully versioned lakehouse pipeline. The result is a transparent, auditable data platform where experimentation is safe and data lineage is clear[9][6]. This approach is on the cutting edge of data engineering, showing how open-source tools can deliver the benefits of a “data repo” in a modern lakehouse.
